Context/Context

Context

管理显式 run_id、配置、插件 DAG、数据访问与缓存诊断的分析入口。

整体介绍

Context 不保存隐式当前运行。每次数据访问都传入 run_id，由它解析插件依赖、准备配置并复用 lineage 一致的缓存。

Context API 迁移

配置更新统一使用 set_config()，它会自动失效解析配置、lineage、缓存键与执行计划。指定 run 的产物清理仍使用 clear_cache_for(run_id, data_name)。内部缓存维护由 Context 管理，私有 helper 不属于用户 API。结果只保存在显式 run 的内存存储中，不再自动创建同名 Context 属性；用户普通属性不会被当作结果，也不会由缓存清理修改。

数据表
原调用当前写法
ctx.<data_name>ctx.get_data(run_id, data_name)
RuntimeCacheManager读取结果用 get_data（缺失时会计算）；检查缓存问题用 diagnose_cache
clear_config_cache() / clear_performance_caches()通过 set_config(...) 更新配置；删除手动维护调用
ctx.profiling_summaryctx.profiler.summary()
analyze_cache() / cache_stats()容量与条目使用 waveform-cache info / stats / list

show_config(run_name=...)保持此写法；run_name 受支持，不发出弃用警告

高级依赖分析及其可视化高亮已退役；拓扑查询不提供缓存命中或重算范围预览。show_config 的 run_name 只标注全局配置视图的缓存目录，不能替代数据访问的 run_id。详细迁移示例见配置管理指南。

python
# 修改配置时自动失效相关内部缓存
ctx.set_config({"threshold": 15}, plugin_name="hit_threshold")
ctx.show_config(run_name="run_001")
lineage = ctx.get_lineage("peaks")
issues = ctx.diagnose_cache("run_001")
print(ctx.profiler.summary())

Context、ExecutorManager 与处理工作流

Context 是单个 run_id 的执行协调层：它解析插件 DAG、确认配置与缓存命中，再按执行计划请求缺失产物。全局 ExecutorManager 是并行资源层：统一管理可复用的线程池/进程池、引用计数、关闭和统计；BatchProcessor 负责把多个 run 拆成彼此隔离的 Context 任务。三者职责不同，但都从本页进入。

数据表
层主要入口职责生命周期边界
Contextget_data(run_id, data_name)解析依赖、resolved config、lineage、缓存与单 run 执行计划每次请求必须显式传入 run_id；不保存隐式当前 run
ExecutorManagerget_executor() / parallel_map() / parallel_apply()创建、复用、统计和关闭 thread/process executor；可选负载均衡池按名称、类型和 worker 数识别；with 退出时释放引用
BatchProcessorprocess_runs() / process_func()编排多个 run 的并发、重试、取消、进度和结果汇总并行任务使用 ctx.clone() 或 ctx.create_context_factory() 隔离 Context
StreamingPluginexecutor_config按配置名或字典选择流式 chunk 的 executor 类型与 worker 数资源配置不应改变产物语义；影响输出的配置仍需进入 lineage

推荐使用路径

python
from concurrent.futures import as_completed

from waveform_analysis import Context
from waveform_analysis import get_config, get_executor
from waveform_analysis.plugins import profiles

run_id = "run_001"
ctx = Context(config={"data_root": "DAQ", "daq_adapter": "vx2730"})
ctx.register(*profiles.cpu_default())

# Context 负责单 run 的 DAG、缓存和产物语义。
peaks = ctx.get_data(run_id, "peaks")

# 公共并行任务通过全局 ExecutorManager 获取资源。
executor_config = get_config("waveform_loading")
with get_executor("waveform-loading", **executor_config) as executor:
    futures = [executor.submit(load_file, path) for path in paths]
    loaded = [future.result() for future in as_completed(futures)]

配置、隔离与缓存不变量

  1. 执行前可用 resolve_dependencies(data_name, run_id=run_id) 查看依赖顺序，用 get_resolved_config(data_name) 检查配置；拓扑顺序不代表本次重算范围。
  2. IO 密集型任务通常选 thread，CPU 密集型任务通常选 process；进程任务的函数、参数和 Context 工厂必须可 pickle。
  3. 复用执行器必须保持稳定的名称、类型和 max_workers；推荐使用 with get_executor(...)，不要依赖内部 _executor_refs。
  4. 多个 run 不共享可变 Context；使用 BatchProcessor 的 context_factory 或显式 ctx.clone()，让每个 run 的缓存和错误边界可追踪。
  5. 显式 context_factory 在串行模式也为每个 run 的每次尝试创建 Context；配置扫描先创建 Context，再应用本组配置，并保留所选缓存策略。
  6. parallel_map() / parallel_apply() 的空列表输入直接返回 []，不创建执行器；执行器的阻塞关闭在注册表锁外进行。
  7. worker 数、进度条和负载均衡属于资源策略；只有改变输出内容、字段或选择的配置才应通过 Plugin track 进入 lineage。
超时支持边界

Plugin.timeout 默认为 None。Context 需要执行 compute() 时拒绝任何非 None 值，计算前抛出 NotImplementedError；有效缓存命中仍可读取，并行 DAG 可能将异常包装为 RuntimeError。独立 TimeoutManager / with_timeout 在 Unix 仅支持主线程的正数超时；Windows 的函数超时只限制等待时间，不能终止后台线程，timeout_context() 不提供执行中断。

边界说明

Context 的 enable_plugin_parallelism/max_parallel_workers 控制同一 run 内的 DAG 分层调度；ExecutorManager 管理公共 thread/process 池和并行辅助函数。不要把 worker 数当作数据产物配置，也不要在多个 run 之间共享同一个可变 Context。

排障顺序

  • 执行计划异常：检查 resolve_dependencies()、get_lineage() 和执行日志。
  • 配置来源异常：检查 get_resolved_config()；不要只看传入 Context 的原始字典。
  • 并行任务泄漏或重复创建：检查执行器名称、reuse、release_executor() 与 get_executor_manager().list_executors()。
  • 进程池失败：先确认函数/参数可序列化，再降低 max_workers 或切换到 thread；不要静默改变 run_id 或缓存目录。

参数

数据表
