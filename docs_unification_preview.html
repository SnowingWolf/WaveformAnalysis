v1 → v2 迁移路径 现有 site-guides.yaml(2 栏目)如何分步扩到全栏目

  1. 内容盘点与清理(前置)
    docs/ 根下 7 个过程性总结(*_SUMMARY / *_fix / *_refactor)归档或删除;4 个正式文档(pre-trigger / 配置 / 查询工具 / Accessor)并入 api / features / plugins 后删除;小目录(visualization / analysis / optimization)并入相邻栏目
  2. schema 升级 + 保留现有栏目
    schema_version 改 2;现有 architecture / plugin-system 先按新字段迁移(plugin-system 加 exclude;插件参考页来源由插件生成器标注)
  3. 逐个加内容目录为栏目
    盘点后保留的目录各一个栏目,source_dirs 自动发现
  4. 配置 exclude 与显式 pages
    排除 reference/**、**/README.md;特殊路由用显式 pages 覆盖
  5. 代码生成参考页归入栏目
    参考页叙述 md 文件头写 tag: reflect(Context/Accessor)或 tag: plugin-provider(插件),生成器识别后归入所属栏目
  6. 逐栏目验证发布
    每加一个栏目即 generate site-web:路由无冲突、栏目齐全、死链校验通过
原则:先内容盘点——不再需要的过程性总结清理,正式文档归并入对应栏目;栏目划分基于「最终需要的文档」,不做机械的一一对应;小目录并入相邻栏目。source_dirs 保留合并能力,但迁移期优先用「盘点后并入」。

tag 标记生成方式 「来源」标注写在文档文件头,生成器扫描时识别

tag 是单页元数据,标注在文档文件头(frontmatter/注释),不是 yaml 里的登记项。 文档放进 source_dirs 目录即可,生成器扫描时读文件头识别 tag,按 tag 分派渲染或注册导航节点。 直接打开 markdown 时这个标注不干扰阅读,但生成器能识别。

tag含义生成器行为
markdown(缺省)手写 md 页面site_guides 渲染;支持 frontmatter / 目录扫描
reflect由代码反射生成(Context / Accessor / records-view)校验路由已由 site_doc_generator 产出,只注册导航节点
plugin-provider由插件生成器产出(插件参考 / DAG)校验路由已由 plugin_doc_generator 产出,只注册导航节点
统一的关键:tag 标注在文档文件头(如 tag: reflect 写在 --- 包裹的 frontmatter 里), 不用在 yaml 里逐页登记。维护者打开文档就知道这页怎么来、改哪里;生成器扫描 source_dirs 时读 frontmatter 识别 tag,分派渲染或注册。

frontmatter 规范 每篇文档的控制放在文件头,而非堆在配置里

---
title: 缓存架构说明      # 覆盖 H1,决定侧边栏标题
summary: 缓存分层、键生成与失效规则
nav_weight: 10            # 同栏目内排序(缺省按文件名序)
exclude_from_nav: false  # true = 进站但不出现在侧边栏
hidden: false             # true = 完全不收录
---
字段用途缺省
title覆盖 H1,用于侧边栏/面包屑H1 文本
summary覆盖首段,用于栏目索引/搜索正文首段
nav_weight同栏目内排序文件名排序
exclude_from_nav进站但不在侧边栏(仍可被链接)false
hidden完全不收录false
mistune 3.3 无内置 frontmatter 插件 → 在 site_guides.py 内自写一个约 15 行解析函数,可控、可单测。

docstring 与 markdown 的配合模型 三层分工,导航统一,各司其职

层事实源在网站中呈现为内容职责
API / 契约 代码 + docstring(签名、参数、返回、插件 provides/config/dtype) API 参考页 —— 罗列方法与签名,如 context.html、accessors、插件页 「是什么 / 长什么样」—— 自动提取,新增公开方法自动同步(现有 Context 反射机制)
指南 markdown(docs/*.md) 教程 / 指南页 —— 讲「怎么用、为什么」 「怎么用 / 为什么」—— 解释与场景
导航 site-guides.yaml 侧边栏菜单 / 首页 / 栏目索引 —— 决定页面组织与顺序 「谁进站、放哪个栏目、什么顺序」—— 页面文件头的 tag 标明生成方式;生成器扫描时读 frontmatter 分派渲染或注册
配合规则(防重复 / 防冲突):
① 事实性内容只写一处 —— 签名 / 参数只在 docstring,解释只在 markdown,不双写;
② 指南页引用参考页用链接锚点(如 context.html#get_data),不复制 API 细节;
③ 生成器里硬编码的叙述块(intro_blocks / _CONTEXT_DESCRIPTIONS)在阶段 A 迁出:契约描述 → docstring,叙述 → docs/ 对应 md,生成器不再写页面文案。

文档多了会不会冲突 冲突在生成期报错,绝不静默覆盖

冲突类型防护机制
路由撞车(两个 md 生成同一 URL) 路由 = 「栏目 id + 文件 stem」确定性生成;生成器检测重复路由 → 直接报错(现有 load_guide_manifest 已检查 duplicate route)
与插件 / 参考页撞(自动扫描到 plugins/ 目录,和插件生成站冲突) 生成器统一校验 guide route 与生成页路由冲突(_publish_guides 已有)→ 报错,用 exclude 排除自动生成目录
链接失效(A 篇链到 B 篇,B 被 exclude / hidden) 生成时对「未收录链接」报 warning(现有 resolve_url);死链校验兜底
同页锚点重复 生成器自动加序号后缀(现有 slug 去重)
导航标题重复(两篇 title 一样,侧边栏混淆) CI 增加「导航重复标题」检查(新增)
误收(草稿 / 内部笔记被自动收进站) 栏目级 exclude:(glob)+ 单篇 hidden: true;可用 _ 前缀文件名约定「不进站」
关键原则:冲突一律在生成时报错、CI 失败,绝不让两篇文档静默互相覆盖。同名文件靠「栏目前缀」天然隔离(不同栏目目录互不撞);每步生成后 git diff + 死链校验,出问题马上定位到具体文件。
